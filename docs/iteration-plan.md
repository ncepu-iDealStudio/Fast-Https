# Fast-Https 开发迭代计划

版本：2026-10-08。本文只排当前代码里还要做的事。已关闭项的过程记录留在 [iteration-hardening-plan.md](iteration-hardening-plan.md)。

## 1. 目标

后面几次迭代把服务变成可以重复发布的状态：配置重载失败时旧服务还在，测试能在持续集成里挡住回归，连接关闭和 HTTP/2 错误有明确行为。

## 2. 已经具备的基线

这些能力已经在代码和测试里，本计划不再排期：

- 启动前校验 `config/fast-https.json` 和 `http.include`
- 缺处理函数的 `location.type` 不会进入监听
- 日志默认写到 `logs/`，控制台 DEBUG/TRACE 走 stderr
- 黑名单、限流、`xss` 有拒绝和放行测试；`sql` 明确不拦截
- 无效配置重载不会替换内存中的 `GConfig`，也不会继续切换监听
- HTTP/2 连接可以发 GOAWAY 并关闭，common 端口可以热更新配置

## 3. 分级

- P0：影响发布或线上恢复
- P1：能运行，但故障时难查、难收口
- P2：协议和维护成本
- P3：体验和后续能力

难易度：易为 0.5–2 天，中为 2–5 天，难为 1–3 周。

## 5. 工作项

### R1 重载信号语义与端到端测试

现状：`reload` 子命令在 Windows 上发控制台 Ctrl+C，在其它平台发 `SIGINT`。进程收到 `SIGINT` 时，Windows 停止服务，其它平台重载配置。`test/client_test/reload_e2e_test.go` 默认跳过，而且只在 Windows 上运行。证书更换没有单独测试。

风险：运维在 Linux 上按 Ctrl+C 会重载，在 Windows 上会停服务。发布前无法在两种系统上用同一条命令证明端口增删。

做法：

- 写明并固定一种语义：要么两边的 `SIGINT` 都表示重载，停止只走 `stop` / `SIGTERM` / `SIGQUIT`；要么在文档和测试里锁定现在的系统差异
- 把 reload 端到端测试从「仅 Windows」扩到当前开发机也能跑的路径，仍然用环境变量开启，避免日常 `go test` 占用端口
- 为证书路径变更补一条用例：新证书生效，坏证书路径不会拆掉旧监听

验收：

- 测试能说明 Windows 与其它平台各自的 `SIGINT` 结果
- 设置环境变量后，端口新增和删除在非 Windows 上也能跑
- 坏的证书配置重载后，原端口仍可接受连接

### R2 持续集成门禁

现状：单测可以在本地执行，仓库里没有把 `go test ./...` 接上的流水线。

风险：合入前没有统一门禁，已经修过的配置校验、重载和防火墙测试可能被后续改动弄坏。

做法：

- 增加一条流水线，在推送和合并请求上执行 `go test ./...`
- 失败时保留包名和测试输出
- 需要环境变量才运行的端到端测试不放进默认门禁

验收：

- 一次故意失败的测试能在流水线里被标红
- 主干上的默认测试通过后才允许合并

### R3 重载后日志文件重新打开

现状：`utils/message` 用 `sync.Once` 打开 `system.log`、`access.log`、`error.log`、`safe.log`。重载配置不会重新按新的 `log_root` 打开文件。

风险：改了日志目录并重载后，新日志仍写进旧文件。

做法：

- 重载成功后关闭旧文件，按当前 `LogRoot` 再打开四份日志
- 打开失败时保留旧的日志输出，并写一条错误

验收：

- 单测在临时目录间切换 `log_root`，重载后新的一行出现在新目录
- 新目录无法创建时，旧目录里的日志文件仍然可写

### R4 连接关闭与请求失败路径

现状：`modules/core/events/events.go` 对解析失败只有一个 TODO。`modules/core/h2/conn/conn.go` 对重复关闭、窗口和部分帧流程仍有未确认分支。`server.go` 的 `initModules` 在监听之后再次初始化安全模块，和启动早期的初始化叠在一起。

风险：客户端提前断开、重载和超时叠在一起时，连接或 goroutine 可能留到进程退出之后。

做法：

- 列出接受、读请求、写响应、重载取消、主动关闭五段的退出条件
- 解析失败和读超时都走同一条关闭函数，重复关闭不再打出新的错误
- 安全模块只保留一处初始化

验收：

- 重复关闭的单测不产生额外错误
- 重载取消后，对应用例里的连接 goroutine 退出

### R5 HTTP/2 与 HPACK 错误分支

现状：HPACK 编解码遇到错误索引时留下 Decoding Error / Encoding Error。帧处理对未知帧是忽略还是报错尚未定。连接级窗口没有检查。`huffman` 的 quickcheck 测试标着 fixme。JSON 数组形式的 XSS 清洗也还没有测试。

风险：畸形头部或窗口耗尽时，连接可能继续读，或者直接中断且没有稳定的错误码。

做法：

- 为非法 HPACK 索引、未知帧、窗口耗尽各定一种结果：返回错误并关闭连接，或明确忽略并记一条调试日志
- 每种结果配一个不访问外网的测试
- 修掉或删除无法稳定通过的 huffman quickcheck；为 XSS 的 JSON 数组补一条清洗测试

验收：

- 上述输入在测试里得到写死的错误或关闭行为
- quickcheck 要么稳定通过，要么不再作为会失败的默认测试

### R6 `status` 命令

现状：`status` 已注册，处理函数直接返回，不读取 `fast-https.pid`，也不报告进程是否存在。

风险：安装成服务之后，操作者无法用同一套命令确认进程还在不在。

做法：

- 读 pid 文件，区分「无 pid 文件」「pid 存在但进程不在」「进程在运行」
- 进程在运行时输出 pid，并以 0 退出；否则以非 0 退出

验收：

- 单测覆盖这三种情况，不要求本机真的启动服务器

### R7 配置文件变更后自动重载

现状：`watchConfigChanges` 只有休眠循环，没有任何调用方。配置变更靠 `reload` 子命令；非 Windows 上也可以发 `SIGINT`。

风险：改完文件如果忘记重载，进程继续用旧配置。自动重载如果赶在 R1 之前做，会把还没定下来的信号语义再包进一层。

做法：

- 放在 R1 完成之后
- 监听 `config/fast-https.json` 和 `http.include` 指向的目录，防抖后调用现有 `server.Reload`
- 沿用已经落地的规则：新文件无效时保留旧配置和旧监听

验收：

- 写入一份有效配置后，监听端口或 `server_name` 切到新值
- 写入一份无效配置后，旧端口仍在，并留下错误日志

### R8 代理上游故障转移

现状：反向代理每个 location 只有一个 `ProxyAddr`。注释里预留了 upstream，还没有健康检查、轮询或失败后换地址。

风险：上游进程退出后，这个 location 的请求会一直失败。

做法：

- 保持单个 `proxy_pass` 的现有 JSON 不变
- 增加可选的上游地址列表。拨号失败时按顺序试下一个地址
- 健康检查和权重放到列表可用之后再做

验收：

- 只有 `proxy_pass` 时，请求仍发到原来的地址
- 配置两个上游且第一个拒绝连接时，请求到达第二个

## 6. 建议节奏

第一批，约一周：

- R2 流水线
- R3 重载后重开日志
- R6 `status`

这三项互相独立，都能用单测或一次流水线运行证明。

第二批：

- R1 重载信号和端到端测试

第三批：

- R4 连接关闭
- R5 HTTP/2 与 HPACK

R7、R8 在 R1 之后单独开。R7 依赖 R1 的信号语义。R8 不要和 R4 的连接改动放在同一次合并里。

## 7. 完成标准

- 默认 `go test ./...` 在流水线里通过
- 无效配置重载后，旧监听还在
- `status` 能区分进程在不在
- HTTP/2 的非法头部、未知帧、窗口耗尽有测试锁定的结果

## 8. 执行约定

- 每项合并时带上能重复运行的测试
- 现有 `config/fast-https.json` 不改字段名也能继续启动
- 行为变化同时改 `README.md` 和本文件的状态表
