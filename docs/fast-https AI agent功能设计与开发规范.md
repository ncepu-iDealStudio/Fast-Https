# fast-https AI Agent 功能设计与开发规范

**文档版本：** V1.1  
**文档性质：** 总体功能设计与技术规范  
**适用项目：** fast-https Web Server 智能运维系统  
**主要用途：** 作为后续源码分析、开发任务拆分、技术方案设计及开发执行计划的依据

# 一、项目背景与建设目标

## 1.1 项目背景

fast-https 是一个自主研发的 Web Server，目标是逐步发展为具备 AI 智能运维能力的 Web 服务器软件。

传统 Web Server 通常具备服务管理、配置管理、日志记录、运行状态监控和异常告警等功能。这些能力能够发现和报告问题，但面对复杂故障时，通常仍然需要管理员人工分析日志、判断原因、制定处理方案并执行修复。

引入 AI Agent 的目的，是在现有服务器运行管理与监控能力的基础上，进一步赋予 fast-https 自主诊断和受控自主修复能力。

最终希望形成一个能够持续运行的智能运维系统：

1. 持续接收服务器运行状态和异常事件。
2. 自动分析异常，关联日志、指标、配置和历史事件。
3. 判断故障原因及影响范围。
4. 制定合理的运维处理方案。
5. 对预先授权的低风险操作进行自动修复。
6. 对高风险操作或无法自主处理的问题升级给管理员。
7. 自动验证修复结果，并记录完整的处理过程。

## 1.2 建设目标

本项目建设的是一个独立运行的 AI 自主运维 Agent，而不是简单地在 Web Server 中增加一个大模型对话接口。

AI Agent 应当具备以下核心能力：

- 事件驱动：能够接收服务器运行过程中产生的异常事件。
- 自主诊断：能够结合运行数据、日志和配置分析故障。
- 计划生成：能够把诊断结果转化为结构化的处理计划。
- 安全决策：能够根据预先定义的权限策略决定是否允许执行。
- 受控执行：能够通过 fast-https 提供的管理接口执行操作。
- 效果验证：能够判断修复是否真正有效。
- 人工协作：无法自主处理时，能够形成完整的人工处理请求。
- 持续改进：保留事件、诊断、修复和验证记录，为后续优化提供依据。

## 1.3 已确定的总体设计决策

| 设计事项 | 已确定方案 |
|---|---|
| Agent 部署位置 | 优先部署在 fast-https 服务器本机 |
| 运行方式 | 独立进程，与 Web Server 解耦 |
| 模型使用策略 | 本地模型优先，必要时使用外部模型 |
| 自主执行权限 | 预授权低风险操作允许自动执行 |
| 高风险操作 | 必须经过人工审批 |
| 运维操作方式 | 优先通过 fast-https CLI / Management API |
| 监控能力 | 复用现有 Server / Monitor 能力 |
| 故障处理方式 | 事件驱动、诊断、计划、执行、验证 |
| 消息基础设施 | 第一阶段不引入复杂 MQ |
| DSH Plugin 定位 | 面向管理员的交互式智能运维入口 |
| 实现语言 | Go。与 Server、Monitor 同一模块，独立进程 `fast-https-agent` |
| 生产依赖 | 不部署必须长期维护的 Python Agent 服务 |

## 1.4 实现语言与技术栈

第一阶段用 Go 实现 Agent。这是工程选择：Agent 的主体是长期运行的运维编排，模型调用只占诊断和方案生成。Python 在 Agent 框架、RAG 和实验工具上更成熟，但不因此把生产进程做成 Python 服务。

| 工作 | Go | Python |
|---|---|---|
| 常驻进程、并发事件、超时与取消 | 与现有 Server 相同的运行方式 | 能做，要另管解释器和依赖 |
| 状态机、策略、调用 CLI、结果验证 | 与 `management/`、`monitor/` 同一语言 | 需要跨语言约定 |
| 调用 OpenAI 兼容 HTTP API | 标准库即可 | SDK 和示例更多 |
| 现成 Agent 框架 | 有，数量少，部分仍是预览版 | LangGraph 等更完整 |
| 分发 | 一个二进制，与 `fast-https`、`fast-https-monitor` 并列 | 需要运行环境 |

因此不在第一阶段引入 LangGraph，也不引入仍处于公开预览的通用 Agent 框架。处理流程已经固定为：收事件、采集上下文、诊断、生成计划、策略检查、执行、验证、完成或升级。这条链路用 Go 状态机实现，权限边界留在策略引擎，不交给框架运行时。

模型侧只保留一个接口。本地推理服务和外部供应商都走 OpenAI 兼容的 HTTP API。模型返回结构化诊断和计划；策略引擎决定能不能执行；执行器只调用白名单里的 fast-https CLI。模型不得到 Shell，也不直接改配置文件。

| 技术模块 | 第一阶段方案 |
|---|---|
| 语言 | Go，模块 `fast-https`，入口 `agent/` |
| HTTP | 标准库 `net/http`。读 `/runtime`，调模型 API |
| 并发 | goroutine、`context` 超时与取消 |
| 持久化 | 单个 SQLite 文件，`database/sql`，纯 Go 驱动，不启用 CGO |
| 状态机 | 自行实现，状态值见第 5 节 |
| 模型 | `ModelProvider` 接口。第一阶段规则诊断不调用它；接口先留好 |
| 配置 | Agent 自己的 JSON 文件，格式对齐 `monitor.json`。不读站点 `fast-https.json`，仓库里也没有 YAML 依赖 |
| 日志 | stderr 上的 JSON 行。不 import `infra/logging`，避免 Agent 依赖 Server 内部包 |
| 健康信息 | 写入状态库，由 `fast-https agent status` 读取。Prometheus 文本导出不在第一阶段 |
| 配置与操作 | 继续用现有 CLI 和 `management/txn`。不新写一套 Management HTTP API |

Python 只用于仓库外的实验：提示词试跑、模型效果对比、日志分析脚本。这些脚本不随安装包发布，也不被 systemd 拉起。若以后某段分析确实不适合放在 Go 里，再单独起一个可选的 HTTP 服务，由 Go Agent 调用。那不是当前的生产结构。

本仓库 `go.mod` 为 `go 1.27.0`，`toolchain go1.27.1`。官方 `github.com/openai/openai-go/v3` 的当前发布要求 Go 1.26 或更高，并建议使用 Go 1.27.2 或该系列更新的补丁，以带上对应的 HTTP/2 修复。第一阶段模型客户端用标准库访问兼容 API，不把该 SDK 加进 `go.mod`。以后若要引入 SDK，先把工具链升到 SDK 文档写明的补丁版本，再单独评审，不在 Agent 功能提交里顺手升级整个 Server 的工具链。

本地模型进程用什么语言部署，与 Agent 语言无关。

## 1.5 目录、模块接口与核心数据

Agent 与 `monitor/` 一样是独立进程：`agent/` 可以引用自己的子包和标准库、选定的 SQLite 驱动，不引用 `runtime/`、`core`、`cmd`、`management/`。分层测试按这个边界加一条。

```text
agent/
  main.go                 进程入口、标志、周期循环
  config.go               Agent 自己的 JSON 配置
  tail.go                 尾读 Monitor events.jsonl
  collect.go              GET /runtime 与白名单 CLI
  diagnose.go             规则诊断
  plan.go                 结构化计划
  policy.go               ALLOW / REQUIRE_APPROVAL / DENY
  execute.go              执行器。第一阶段不发出写命令
  verify.go               验证器。第一阶段只处理 recovered 关闭任务
  audit.go                追加审计
  escalate.go             待审批与升级
  store.go                SQLite 读写
  model/provider.go       ModelProvider
  model/router.go         本地优先、失败降级、超时
  model/local/openai_compatible.go
  model/external/openai.go
```

`fast-https` CLI 只读查询放在 `management/agentview` 和 `cmd/agent.go`，与 `monview` 相同：只读 SQLite，不 import `agent/`。

模型接口：

```go
type ModelProvider interface {
    Generate(ctx context.Context, req ModelRequest) (*ModelResponse, error)
}

type ModelRequest struct {
    Purpose      string          // diagnose 或 plan
    System       string
    User         string
    JSONSchema   json.RawMessage // 调用方期望的结构，可空
}

type ModelResponse struct {
    Provider string
    Model    string
    Content  json.RawMessage // 必须能被对应 Go 类型反序列化，否则视为调用失败
}
```

`router.go` 的顺序是本地 Provider，超时或连接失败再试外部 Provider。两者都失败时，规则诊断的结果仍然有效，任务按「模型不可用」升级，不把失败当成允许执行。`Generate` 的实现不注册工具，不返回可执行命令。

SQLite 文件默认：

- 归档布局：`./state/agent/agent.db`
- 包布局：`/var/lib/fast-https/agent/agent.db`
- 测试：`FASTHTTPS_AGENT_DIR`

逻辑表与第 14 节实体对应。审计表只插入。任务状态变更写 `updated_at`。`plan_hash` 是计划参数的哈希，审批若将来绑定，必须对上这个哈希。

```text
agent_event(event_id PRIMARY KEY, monitor_type, severity, summary, received_at, source, snapshot_started_at)
agent_task(task_id PRIMARY KEY, event_id, status, attempts, context_json, created_at, updated_at)
agent_diagnosis(task_id PRIMARY KEY, classification, subject, cause, impact, evidence_json, needs_human)
agent_plan(plan_id PRIMARY KEY, task_id, event_id, risk, plan_hash, steps_json, needs_approval)
agent_approval(plan_id PRIMARY KEY, status, reason, created_at)
agent_audit(id INTEGER PRIMARY KEY, at, task_id, kind, payload_json)
agent_offset(id INTEGER PRIMARY KEY CHECK (id = 1), monitor_offset)
```

`snapshot_started_at` 只用于把 `recovered` 对上同一次启动里的 `unreachable`，不作为新的 Monitor 字段。

`agent_operation` 仍不建表。真正执行现有 CLI 写命令时，沿用 `management/operation` 的 `operation_id`，Agent 只在审计里记下这个 ID。

第一阶段任务状态使用第 5.1 节的子集：`PENDING`、`COLLECTING`、`DIAGNOSING`、`PLANNING`、`POLICY_CHECK`、`WAITING_APPROVAL`、`COMPLETED`、`FAILED`、`ESCALATED`、`IGNORED`。没有写操作时不进入 `EXECUTING` 和 `VERIFYING`。

# 二、总体架构设计

## 2.1 三层架构

整个 fast-https 智能运维体系由三个相互独立、协同工作的部分组成。

### 第一层：交互式智能运维助手

**组件：fast-https DSH Plugin**

主要面向管理员，提供自然语言交互和远程运维能力。

主要功能：

- 自然语言理解管理员的运维需求。
- 查询服务器运行状态。
- 查看和分析服务器日志。
- 诊断指定故障。
- 分析配置文件和配置变更。
- 生成运维建议和配置修改方案。
- 查看 AI Agent 的故障处理记录。
- 查看和审批 AI Agent 提交的待审批操作。
- 人工授权后执行指定运维操作。
- 对 AI Agent 的诊断结果和处理过程进行解释。

DSH Plugin 是交互式智能运维助手，不承担服务器 7×24 小时持续监控任务，也不作为 AI Agent 的运行宿主。

### 第二层：AI 自主运维 Agent

**组件：fast-https AI Agent**

这是本项目新增的核心智能运维组件。

主要功能：

- 接收 Monitor 产生的异常事件。
- 收集故障相关上下文。
- 分析故障类型和可能原因。
- 判断故障影响范围。
- 生成结构化运维计划。
- 根据安全策略判断操作权限。
- 自动执行预授权低风险操作。
- 创建需要人工审批的运维操作。
- 验证修复效果。
- 记录完整处理过程。
- 对无法处理的故障进行人工升级。

AI Agent 应独立运行，不依赖 DSH Host。

即使 DSH Host 没有运行，AI Agent 仍然能够接收事件、执行预授权修复和记录待审批事项。

### 第三层：服务器原生运行与监控能力

**组件：fast-https Native Core / Monitor**

主要由 fast-https Web Server 现有功能及其配套监控能力组成。

职责包括：

- Web Server 正常运行。
- 服务生命周期管理。
- Runtime 运行状态和指标采集。
- 请求、连接和响应统计。
- Upstream 健康状态检测（如果支持）。
- 日志记录。
- 异常检测和事件生成。
- 配置读取、校验、应用和版本管理。
- 管理操作执行及结果验证。
- 必要时向外部告警系统发送通知。

这一层应以原生代码和确定性规则为主，不依赖大模型。

### 2.2 总体架构关系

```text
                    管理员
                      |
                      v
          DSH Host / DSH Plugin
          交互式智能运维助手
                      |
              SSH / CLI / API
                      |
        +-------------+-------------+
        |                           |
        v                           v
  fast-https AI Agent        Native Core / Monitor
  自主运维智能体              服务器原生能力
        |                           |
        |<------ 异常事件 -----------|
        |
        +---- 上下文采集
        |
        +---- 故障诊断
        |
        +---- 运维计划生成
        |
        +---- 安全策略校验
        |
        +---- 受控操作执行
        |
        +---- 修复效果验证
        |
        +---- 审计与人工升级
                    |
          +---------+---------+
          |                   |
          v                   v
       修复成功             需要人工
          |                   |
          v                   v
       事件关闭          待审批/人工处理
                              |
                              v
                         DSH Plugin
```

### 2.3 核心架构原则

1. AI Agent 不应成为 Web Server 正常运行的必要依赖。
2. Monitor 不应依赖大模型完成基础指标采集和阈值检测。
3. AI Agent 不直接修改正式配置文件。
4. AI Agent 不拥有任意 Shell 执行权限。
5. 所有实际运维操作必须通过受控管理接口执行。
6. 模型输出不能直接作为执行授权依据。
7. 所有重要操作必须具有持久化记录和可查询结果。
8. DSH Plugin 与 AI Agent 相互独立，通过管理接口和审批机制协作。
9. 先复用现有能力，避免重复建设。

# 三、AI Agent 内部模块设计

AI Agent 第一阶段建议采用单个独立进程、模块化内部结构，不需要拆分为多个微服务。

## 3.1 模块划分

建议包含以下模块：

| 模块 | 职责 |
|---|---|
| Event Receiver | 接收、校验和持久化异常事件 |
| Event Queue | 管理待处理事件和处理状态 |
| Context Collector | 采集故障相关上下文 |
| Diagnosis Engine | 执行规则诊断和 AI 故障分析 |
| Planner | 生成结构化运维处理计划 |
| Policy Engine | 判断操作是否符合授权策略 |
| Action Executor | 调用 CLI / Management API 执行操作 |
| Verification Engine | 验证修复效果 |
| Audit Manager | 保存事件、诊断、计划和执行记录 |
| Escalation Manager | 创建人工审批事项和升级请求 |
| Model Router | 管理本地模型和外部模型调用 |

以上是逻辑模块，不要求每个模块独立部署。

## 3.2 Event Receiver：事件接收器

负责接收 fast-https Monitor 产生的异常事件。

基本要求：

- 支持结构化事件输入。
- 校验事件格式和必要字段。
- 根据事件 ID 实现幂等处理。
- 对重复事件进行去重。
- 将有效事件持久化。
- 创建待处理任务。
- 记录事件来源和接收时间。

第一阶段不另开 HTTP 或 Unix 套接字。Agent 尾读 Monitor 已经写下的 `events.jsonl`。推送通道留到以后，避免改 Monitor 的落盘格式。

不建议第一阶段引入 Kafka、RabbitMQ 等复杂消息中间件。

## 3.3 Event Queue：事件队列

用于管理尚未处理、正在处理和已经处理的事件。

建议支持以下状态：

- PENDING：等待处理。
- PROCESSING：正在处理。
- WAITING_APPROVAL：等待人工审批。
- COMPLETED：处理完成。
- FAILED：处理失败。
- ESCALATED：已升级人工。
- IGNORED：经规则判断无需处理。

基本要求：

1. Agent 重启后能够恢复未完成事件。
2. 同一事件不能被多个工作线程重复执行。
3. 支持失败重试和最大重试次数。
4. 支持事件优先级。
5. 支持事件超时和过期处理。
6. 重要状态变更必须持久化。

第一阶段使用一个 SQLite 文件保存队列和任务状态，不引入独立消息服务，也不使用 Server 的配置状态目录。表结构见第 1.5 节。

## 3.4 Context Collector：上下文采集器

负责围绕异常事件收集诊断所需的数据。

建议包含以下数据类型：

| 数据类别 | 具体内容 |
|---|---|
| 服务状态 | 服务是否运行、运行时间、版本 |
| 请求指标 | 请求量、错误率、响应耗时 |
| 连接指标 | 活动连接数、连接失败情况 |
| Upstream | 节点状态、连接失败率、响应耗时 |
| 系统资源 | CPU、内存、磁盘使用情况 |
| 日志 | 故障发生前后的相关日志 |
| 配置 | 当前生效配置、配置版本 |
| 历史事件 | 最近发生的相关异常 |
| 操作记录 | 最近的配置修改、证书操作、服务操作 |

具体采集项目以 fast-https 当前已有能力为准。

对于缺失的数据，先评估是否需要补充 Runtime API 或 Metrics API，不应重复开发已经存在的能力。

上下文采集应遵循最小必要原则，避免无关日志和过大的数据内容直接进入模型上下文。

## 3.5 Diagnosis Engine：故障诊断引擎

采用规则诊断与 AI 分析相结合的方式。

### 规则诊断

适用于明确、确定性较高的问题，例如：

- CPU 使用率超过阈值。
- 磁盘空间不足。
- 证书即将过期。
- Upstream 健康检查失败。
- HTTP 错误率超过阈值。
- 服务进程异常退出。

### AI 诊断

适用于需要多源信息关联和推理的问题，例如：

- 多种日志异常之间的关联。
- 502 / 504 错误的复杂原因分析。
- 配置修改后出现的性能异常。
- 多个异常同时发生时的根因判断。
- 复杂故障的处理方案分析。

### 诊断结果要求

诊断引擎应输出结构化结果，至少包含：

- 故障分类。
- 故障对象。
- 可能原因。
- 影响范围。
- 证据和关联数据。
- 判断置信度。
- 建议处理方式。
- 是否适合自动修复。
- 是否需要人工介入。

模型给出的置信度仅作为参考，不构成执行权限依据。

## 3.6 Planner：运维计划生成器

将诊断结果转化为可以执行或审批的结构化计划。

每个计划至少应包含：

- 计划 ID。
- 关联事件 ID。
- 故障描述。
- 诊断结果。
- 目标资源。
- 操作步骤。
- 每一步的操作参数。
- 操作风险等级。
- 预期结果。
- 验证方法。
- 失败处理方式。
- 是否需要人工审批。

Planner 只负责提出计划，不拥有实际执行权限。

计划必须经过 Policy Engine 校验后才能进入执行阶段。

## 3.7 Policy Engine：安全策略引擎

这是 AI Agent 最重要的安全模块之一。

负责判断计划中的操作是否允许执行。

核心原则：

**LLM 不能决定自己拥有什么权限，权限由独立策略系统控制。**

策略检查至少包括：

1. 操作类型是否在允许列表中。
2. 目标资源是否属于允许管理的范围。
3. 操作参数是否合法。
4. 是否满足操作前置条件。
5. 是否存在冲突操作。
6. 是否超过执行频率限制。
7. 是否超过自动修复次数。
8. 是否需要人工审批。
9. 是否存在明确的回滚或失败处理方式。

策略判断结果应包含：

- ALLOW：允许自动执行。
- REQUIRE_APPROVAL：需要人工审批。
- DENY：禁止执行。

策略配置应独立于模型提示词，不能由模型动态修改。

## 3.8 Action Executor：运维执行器

负责执行经过授权的操作。

执行方式：

- 优先调用 fast-https CLI。
- 对 CLI 不适合的功能调用 Management API。
- 不直接修改正式配置文件。
- 不开放任意 Shell 命令。
- 不允许模型生成命令后未经校验直接执行。

所有执行操作应具备：

- operation_id。
- request_id。
- 操作类型。
- 目标资源。
- 操作参数。
- 执行时间。
- 执行状态。
- 执行结果。
- 错误信息。

对于配置变更，应复用 fast-https 管理核心提供的事务能力，包括配置校验、备份、原子切换、reload、结果验证和回滚。

对于重要操作，必须能够查询执行状态，避免因通信中断造成重复执行。

## 3.9 Verification Engine：修复验证器

操作执行成功不等于故障修复成功。

验证器需要重新采集相关运行指标，判断故障是否恢复。

例如：

Upstream 节点异常处理后，需要检查：

- Upstream 健康状态是否恢复。
- 请求成功率是否提高。
- 502 / 504 错误率是否下降。
- 业务请求是否能够正常完成。

验证结果：

- SUCCESS：故障已经恢复。
- PARTIAL_SUCCESS：部分恢复。
- FAILED：修复未成功。
- UNKNOWN：当前无法确认。

验证失败时，应停止无休止的自动尝试，并根据策略决定回滚、熔断或升级人工。

## 3.10 Audit Manager：审计管理器

记录完整的故障处理过程。

至少记录：

- 原始异常事件。
- 上下文采集结果。
- 诊断结论。
- 模型调用信息。
- 生成的运维计划。
- 策略判断结果。
- 实际执行操作。
- 执行结果。
- 验证结果。
- 人工审批记录。
- 最终事件处理状态。

审计记录应支持按事件、时间、资源、操作类型查询。

## 3.11 Escalation Manager：人工升级管理器

当 Agent 无法自主处理问题时，负责形成待处理事项。

触发条件包括：

- 诊断结果不明确。
- 不存在可用的自动修复动作。
- 修复计划需要人工审批。
- 自动修复失败。
- 达到最大重试次数。
- 触发安全熔断。
- 模型不可用且规则无法处理。

人工升级事项应包含故障描述、证据、诊断结果、建议方案、风险说明和待审批操作。

# 四、事件协议设计

## 4.1 事件数据结构

Monitor 与 AI Agent 之间应采用统一的结构化事件协议。

建议事件基本结构：

```json
{
  "event_id": "evt_20261109_00001",
  "event_type": "upstream_unhealthy",
  "severity": "critical",
  "source": "fast_https_monitor",
  "timestamp": "2026-11-09T10:30:00+08:00",
  "server_id": "server_001",
  "resource": {
    "type": "upstream",
    "name": "backend_api"
  },
  "summary": "Upstream 节点健康状态异常",
  "metrics": {},
  "evidence_refs": [],
  "status": "open"
}
```

上述字段是目标协议，不是 Monitor 当前的文件格式。当前一行是 `time`、`type`、`rule`、`severity`、`message`、`event_id` 和可选的 `snapshot`。第一阶段不改这个格式。

Agent 读到合法的 `event_id`（32 位十六进制）就直接用。旧行没有该字段时，用与 `monitor/events.go` 的 `eventID` 相同的输入补一个：`type`、`severity`、`message`，以及 `snapshot` 里的 pid 和 `started_at`。不含时间，也不含文件偏移。

## 4.2 事件类型

第一阶段建议覆盖：

| 事件类型 | 说明 |
|---|---|
| upstream_unhealthy | Upstream 节点异常 |
| http_error_spike | HTTP 错误率异常 |
| service_unavailable | 服务不可用 |
| high_resource_usage | 系统资源异常 |
| certificate_expiring | 证书即将过期 |
| certificate_renew_failed | 证书续期失败 |
| disk_space_low | 磁盘空间不足 |
| config_apply_failed | 配置应用失败 |

事件协议应允许后续扩展，不应把事件类型写死在 Agent 核心代码中。

# 五、故障处理状态机

AI Agent 应当采用明确的状态机管理每一次故障处理任务。

## 5.1 状态定义

| 状态 | 含义 |
|---|---|
| PENDING | 等待处理 |
| COLLECTING | 正在采集上下文 |
| DIAGNOSING | 正在诊断 |
| PLANNING | 正在生成计划 |
| POLICY_CHECK | 正在进行权限检查 |
| WAITING_APPROVAL | 等待人工审批 |
| EXECUTING | 正在执行操作 |
| VERIFYING | 正在验证修复效果 |
| COMPLETED | 处理成功 |
| FAILED | 处理失败 |
| ESCALATED | 已升级人工 |
| CANCELLED | 已取消 |

## 5.2 典型处理流程

```text
异常事件产生
     |
     v
事件接收与持久化
     |
     v
上下文采集
     |
     v
故障诊断
     |
     v
生成运维计划
     |
     v
安全策略检查
     |
     +-----------------------+
     |                       |
     v                       v
允许自动执行              需要人工审批
     |                       |
     v                       v
执行修复                创建待审批事项
     |                       |
     v                       v
修复验证                等待管理员确认
     |                       |
     v                       v
处理成功/失败             授权后执行
     |                       |
     +-----------+-----------+
                 |
                 v
              审计记录
                 |
                 v
              事件结束
```

## 5.3 状态管理要求

- 每次状态变化都应持久化。
- Agent 重启后能够恢复未完成任务。
- 事件处理失败应保留失败原因。
- 人工审批不能依赖 DSH Plugin 一直在线。
- 同一事件不能因为重复投递而重复执行危险操作。
- 超时和重试必须有明确上限。
- 事件关闭应有明确的验证依据。

# 六、自主运维权限体系

## 6.1 权限等级

采用三级权限模型。

| 等级 | 名称 | 说明 |
|---|---|---|
| L1 | 自动分析 | 查询、分析、诊断和生成建议 |
| L2 | 受限自动修复 | 执行预先授权的低风险操作 |
| L3 | 高风险运维 | 需要管理员明确审批后执行 |

## 6.2 第一阶段建议权限表

| 操作 | 权限 |
|---|---|
| 查询服务状态 | L1 |
| 查询运行指标 | L1 |
| 查询日志 | L1 |
| 分析配置 | L1 |
| 生成故障诊断报告 | L1 |
| 生成修复方案 | L1 |
| 摘除故障 Upstream 节点 | 满足条件时 L2 |
| 恢复 Upstream 节点 | 满足条件时 L2 |
| 清理指定范围临时缓存 | 条件允许时 L2 |
| 修改站点配置 | L3 |
| 修改监听端口 | L3 |
| 证书更新或替换 | L3 |
| 重启服务 | L3 |
| 删除站点或证书 | 禁止自主执行 |
| 任意 Shell 命令 | 禁止 |

以上操作权限属于目标权限，不是当前可执行清单。摘除上游、恢复上游和清理缓存在补齐计划 C6 提供对应命令之前，策略引擎固定为 DENY，不能因为本表写成 L2 就自动执行。

## 6.3 L2 自动修复约束

自动修复必须满足以下条件：

1. 操作类型已经进入授权白名单。
2. 目标资源明确。
3. 操作参数经过校验。
4. 操作前置条件全部满足。
5. 不会导致关键业务资源全部不可用。
6. 操作次数未超过限制。
7. 不存在冲突操作。
8. 有明确的验证方法。
9. 有预定义的失败处理方式。

例如，自动摘除 Upstream 节点时，必须确认至少存在满足业务要求的健康替代节点。

不能由 LLM 自己判断某个操作是否属于低风险。

## 6.4 安全保护机制

第一阶段至少应具备：

- 最大自动修复次数。
- 同类故障冷却时间。
- 操作超时时间。
- 连续失败熔断。
- 幂等执行。
- 操作前置条件检查。
- 操作后结果验证。
- 重要操作审计。
- 人工审批机制。

# 七、模型管理与调用设计

## 7.1 模型使用原则

采用本地模型优先、外部模型备用的方式。

AI Agent 不应直接依赖某一个模型服务或厂商。

建议通过 Model Router 统一管理模型调用。接口、目录和降级顺序见第 1.5 节。第一阶段的规则诊断不调用模型。

## 7.2 模型调用架构

```text
          AI Agent
              |
              v
          Model Router
              |
        +-----+------+
        |            |
        v            v
    Local Model   External Model
      优先使用       按策略备用
```

## 7.3 任务路由

| 任务类型 | 推荐方式 |
|---|---|
| 简单故障分类 | 规则或本地模型 |
| 日志异常关联 | 本地模型优先 |
| 常规故障诊断 | 本地模型优先 |
| 复杂根因分析 | 本地模型能力不足时考虑外部模型 |
| 结构化运维计划 | 本地模型优先 |
| 权限判断 | 独立 Policy Engine，不交给模型 |

## 7.4 模型调用要求

- 统一模型调用接口。
- 支持模型超时。
- 支持失败重试，但必须有上限。
- 支持模型不可用时降级。
- 支持结构化输出校验。
- 支持模型调用日志和耗时记录。
- 支持本地模型和外部模型分别配置。
- 支持模型切换而不影响 Agent 其他模块。

## 7.5 数据安全

外部模型调用必须经过数据安全检查。

默认不应将以下信息直接发送到外部模型：

- 服务器账号和密码。
- 证书私钥。
- API Token。
- 内部网络拓扑。
- 敏感配置内容。
- 未脱敏的用户信息和访问日志。

应根据配置决定哪些信息允许外发，必要时进行脱敏和摘要处理。

## 7.6 模型不可用时的处理

| 情况 | 处理方式 |
|---|---|
| 本地模型正常 | 正常诊断 |
| 本地模型超时 | 根据策略尝试外部模型 |
| 外部模型不可用 | 使用规则能力降级 |
| 所有模型不可用 | 保存事件，等待恢复或升级人工 |
| 模型输出格式错误 | 校验失败，不允许进入执行阶段 |

模型服务故障不得影响 Web Server 的正常运行。

# 八、与 fast-https 现有管理能力的集成

## 8.1 基本原则

AI Agent 不应重新实现一套服务器管理功能。

应尽量复用现有 fast-https CLI、Management API 和管理核心。

建议集成能力：

| 能力 | 优先调用方式 |
|---|---|
| 查询服务状态 | CLI / Management API |
| 查询运行指标 | Runtime API / Metrics API |
| 查询日志 | CLI / 日志接口 |
| 查询配置 | CLI / Management API |
| 查询 Upstream 状态 | Runtime API |
| Upstream 节点管理 | CLI / Management API |
| 配置检查 | CLI |
| 配置应用 | 管理核心 |
| 配置回滚 | 管理核心 |
| 服务操作 | 现有服务管理能力 |
| 查询操作状态 | Management API / CLI |

最终以源码扫描确认的实际能力为准。

## 8.2 配置管理安全要求

Agent 不得直接修改正式配置文件。

正式配置修改必须由 fast-https 管理核心完成。

管理核心应负责：

1. 接收结构化配置变更请求。
2. 校验变更参数。
3. 生成新配置。
4. 检查配置合法性。
5. 备份原配置。
6. 原子切换配置。
7. 执行必要的 reload。
8. 验证服务状态。
9. 失败时执行回滚。
10. 保存操作结果。

如果现有管理核心尚不具备这些能力，应先评估需要补充的部分。

## 8.3 操作持久化

重要操作必须支持：

- request_id。
- operation_id。
- 操作状态查询。
- 幂等请求。
- 执行结果持久化。
- 操作后回读验证。

对于通信中断、进程重启等情况，Agent 应能够查询原操作状态，而不是盲目重复执行。

# 九、与 DSH Plugin 的协作机制

## 9.1 职责边界

| 功能 | AI Agent | DSH Plugin |
|---|---|---|
| 持续监控 | 通过 Monitor 接收事件 | 否 |
| 自动故障诊断 | 是 | 是 |
| 自动修复 | 预授权范围内 | 经管理员授权后 |
| 人工审批 | 创建待审批事项 | 提供审批入口 |
| 查看历史事件 | 是 | 是 |
| 自然语言交互 | 非必要 | 是 |
| 远程运维 | 非主要职责 | 是 |
| 自动处理失败升级 | 是 | 协助处理 |

## 9.2 人工审批流程

当 AI Agent 生成的操作计划需要人工审批时：

1. 创建 Pending Operation。
2. 持久化操作计划及其参数。
3. 记录审批原因和风险说明。
4. 通过告警或管理接口通知管理员。
5. DSH Plugin 查询待审批事项。
6. 管理员确认或拒绝。
7. Agent 校验审批是否仍然有效。
8. 执行或取消操作。
9. 记录最终结果。

审批应绑定明确的计划版本、目标资源和操作参数。

审批后若操作参数发生变化，必须重新审批。

DSH Plugin 暂时离线时，待审批事项仍应保存在服务器端。

# 十、部署与运行设计

## 10.1 默认部署方式

第一阶段优先采用本机部署。

建议部署结构：

```text
fast-https-server/
    |
    +-- fast-https
    |
    +-- fast-https-monitor
    |
    +-- fast-https-agent
    |
    +-- Local Model Runtime（可选，独立进程）
    |
    +-- state/agent/agent.db
```

三个 Go 程序分开部署、分开启停。Agent 使用与 Server、Monitor 相同的模块和构建方式。本地模型运行时仍然单独安装，这一项与 Agent 是否用 Go 无关。

AI Agent、Monitor 和 Web Server 应保持独立进程。

本地模型运行时可以独立部署，也可以配置在其他可访问的本地推理节点上。

本机优先不意味着必须将所有模型推理工作放在 Web Server 所在设备上。

## 10.2 资源隔离

必须避免 AI Agent 或模型推理影响 Web Server 的核心业务。

建议具备：

- Agent 最大 CPU 使用限制。
- Agent 最大内存使用限制。
- 模型调用超时。
- 模型调用并发限制。
- 事件处理并发限制。
- 日志采集大小限制。
- 上下文长度限制。
- 任务执行超时。

具体数值应通过目标服务器硬件和实际压力测试确定，不在总体规范中提前假设。

## 10.3 运行可靠性

- Agent 崩溃不影响 Web Server。
- Agent 重启后恢复未完成任务。
- Monitor 不依赖 Agent 运行。
- 模型不可用时系统能够降级。
- 事件和操作记录持久化。
- 对重复事件和重复请求进行幂等处理。
- Agent 应具备自身健康状态和运行日志。

# 十一、安全设计

## 11.1 Prompt Injection 防护

服务器日志、HTTP 请求内容、User-Agent、URL Path、配置注释等都可能包含外部输入。

这些内容必须视为不可信数据。

不能因为内容被传入大模型，就将其当成可信指令。

安全要求：

1. 外部输入不能改变 Agent 系统指令。
2. 日志内容不能授权 Agent 执行操作。
3. 模型不能自行扩展权限。
4. 模型不能绕过 Policy Engine。
5. 模型不能直接执行任意 Shell。
6. 结构化操作参数必须进行严格校验。
7. 敏感信息应进行过滤或脱敏。

## 11.2 最小权限原则

AI Agent 只应拥有完成授权任务所需要的权限。

不应默认拥有：

- Root 权限。
- 任意文件读写权限。
- 任意 Shell 执行权限。
- 任意网络访问权限。
- 任意证书私钥读取权限。

如果部分操作确实需要较高系统权限，应通过受控的管理接口或权限隔离机制实现。

## 11.3 审计要求

所有自动修复和人工授权操作都必须保留审计记录。

审计记录应能够回答：

- 为什么发生故障？
- Agent 收到了什么事件？
- 收集了哪些证据？
- AI 得出了什么结论？
- 生成了什么操作计划？
- 策略引擎为什么允许或拒绝？
- 实际执行了什么操作？
- 修复结果如何？
- 是否发生人工审批？

---

# 十二、第一阶段故障场景与建设范围

第一阶段不追求覆盖所有 Web Server 故障。

建议优先选取三个典型场景，验证自主运维闭环。

## 12.1 场景一：Upstream 节点异常

目标：验证 Agent 能否自主完成一个范围明确、条件可检查的低风险修复任务。

处理流程：

1. Monitor 发现 Upstream 节点健康检查异常。
2. 产生结构化事件。
3. Agent 收集节点状态和相关日志。
4. 诊断故障原因。
5. 判断是否存在健康替代节点。
6. 生成节点摘除计划。
7. Policy Engine 检查自动修复条件。
8. 满足条件时自动执行。
9. 验证 Upstream 状态和 HTTP 请求情况。
10. 成功后关闭事件，失败时熔断并升级人工。

注意：当前 `proxy_pass` 仍是单个地址，没有摘除命令。第一阶段只做到第 6 步的计划，策略结果为 DENY 或待审批，不执行第 8、9 步。自动摘除留到补齐计划 C6。

## 12.2 场景二：502 / 504 异常增加

目标：验证 AI Agent 对多个信息源进行关联分析的能力。

处理流程：

1. Monitor 检测到 502 / 504 错误率异常。
2. Agent 收集请求指标、Upstream 状态和日志。
3. 分析故障发生时间和影响范围。
4. 关联近期配置变更和服务操作。
5. 判断可能原因。
6. 生成故障诊断报告。
7. 给出处理建议。
8. 对需要修改配置或重启服务的操作，提交人工审批。

第一阶段以 L1 自动分析为主，不强制实现自主修复。

## 12.3 场景三：证书即将过期或续期失败

目标：验证证书管理相关的异常分析和人工协作能力。

处理流程：

1. Monitor 检测证书即将过期或续期失败。
2. Agent 查询证书状态和续期记录。
3. 收集相关日志。
4. 分析失败原因。
5. 生成处理建议。
6. 对需要更新、替换证书等操作，提交人工审批。
7. 执行经批准的操作后验证证书状态。

第一阶段不允许 Agent 自主覆盖证书私钥或执行未经审批的高风险证书操作。

# 十三、第一阶段开发范围与优先级

第一阶段的核心目标是建立完整的自主运维闭环，而不是开发一个功能繁多的通用 Agent 平台。

## 13.1 P0：自主运维闭环基础能力

| 模块 | 开发内容 |
|---|---|
| 现有能力扫描 | 检查 Server、Monitor、CLI、API 能力 |
| 事件接收 | 事件协议、接收、校验、去重 |
| 事件持久化 | 事件状态、处理任务和恢复机制 |
| 上下文采集 | 指标、日志、配置和历史事件 |
| 故障诊断 | 规则诊断及 AI 诊断基础能力 |
| 计划生成 | 结构化运维计划 |
| Policy Engine | 操作白名单和权限检查 |
| Action Executor | 受控 CLI / API 调用 |
| Verification | 修复结果验证 |
| Audit | 事件和操作审计 |
| Escalation | 人工升级和待审批事项 |

## 13.2 P1：模型和人工协作

- 本地模型适配。
- 外部模型备用机制。
- 模型路由和降级。
- DSH Plugin 待审批接口。
- 管理员审批及拒绝机制。
- 更多故障诊断场景。

## 13.3 P2：能力扩展

- 更多故障类型。
- 更复杂的多事件关联分析。
- 历史故障案例辅助诊断。
- 自动修复策略扩展。
- 运维效果统计。
- 诊断质量和修复成功率分析。

第一阶段不建议开发多 Agent 协作框架、复杂工作流平台或独立知识图谱系统。

# 十四、数据持久化设计建议

AI Agent 需要保存事件、任务、诊断、计划、操作、审批和审计记录。

第一阶段建议优先考虑以下逻辑数据实体：

| 实体 | 用途 |
|---|---|
| agent_event | 接收的异常事件 |
| agent_task | 事件对应的处理任务 |
| agent_diagnosis | 故障诊断结果 |
| agent_plan | 运维处理计划 |
| agent_operation | 实际运维操作 |
| agent_approval | 人工审批记录 |
| agent_audit_log | 完整审计记录 |

以上是逻辑实体。第一阶段落在同一个 SQLite 文件里，表名与实体对应，见第 1.5 节。不为此新建数据库服务。

Server 侧已有的 operation 记录继续放在 `management/state`，不并入 Agent 的库。

需要保证：

- 事件 ID 唯一。
- 任务与事件关联。
- 计划与操作关联。
- 审批与具体计划版本关联。
- 操作状态可以查询。
- 审计记录不可被普通任务随意修改。
- 任务状态变更具有明确的时间记录。

# 十五、第一阶段验收标准

第一阶段不以模型调用成功作为主要验收标准，而应以实际故障处理闭环作为验收依据。

## 15.1 基础能力验收

- [ ] Agent 能够独立启动和运行。
- [ ] Agent 与 Web Server 进程解耦。
- [ ] 能够接收 Monitor 产生的结构化事件。
- [ ] 能够持久化事件和处理状态。
- [ ] 能够在重启后恢复未完成任务。
- [ ] 能够采集故障所需上下文。
- [ ] 能够生成结构化诊断结果。
- [ ] 能够生成结构化运维计划。

## 15.2 安全能力验收

- [ ] 存在独立 Policy Engine。
- [ ] 具有操作白名单。
- [ ] 模型不能直接执行 Shell。
- [ ] 未授权操作不能执行。
- [ ] 高风险操作必须人工审批。
- [ ] 自动修复具备最大重试次数。
- [ ] 自动修复具备冷却和熔断机制。
- [ ] 重要操作具有幂等机制。
- [ ] 关键操作具有审计记录。

## 15.3 修复能力验收

第一阶段（执行计划 A1–A6）验收这些：

- [ ] 无法自动处理时写入待审批或升级记录。
- [ ] 能够查询待审批操作。
- [ ] 不执行配置、reload、摘除节点、证书续期或重启。

下列条目留到 C6 或 C7 提供受控写命令之后，本阶段不作为验收失败：

- [ ] 能够执行至少一种预授权低风险修复。
- [ ] 能够验证修复结果。
- [ ] 能够记录人工审批结果并按该结果执行。
- [ ] 修复失败后能够停止重复尝试。

## 15.4 稳定性验收

- [ ] Agent 停止不影响 Web Server。
- [ ] 本地模型不可用不影响 Web Server。
- [ ] 外部模型不可用时能够降级。
- [ ] Agent 重启后能够恢复任务状态。
- [ ] Agent 资源消耗不会明显影响 Web Server。
- [ ] 重复事件不会造成重复的危险操作。

具体性能指标、资源限制、修复成功率和响应时间，应在开发计划阶段结合目标服务器硬件及测试环境确定。

# 十六、明确不属于第一阶段的建设内容

为了控制项目复杂度，第一阶段暂不建设：

1. 多 Agent 自主协作体系。
2. 通用 AI 工作流引擎。
3. 大规模知识图谱。
4. 独立消息中间件集群。
5. 任意 Shell 自动执行能力。
6. 全自动配置修改和服务重启。
7. 覆盖所有 Web Server 故障类型的通用修复平台。
8. DSH Host 常驻托管 AI Agent。
9. 依赖外部大模型才能运行的监控系统。
10. 以 Python 或通用 Agent 框架作为生产进程。
11. 在第一阶段引入官方模型 SDK。模型访问使用标准库 HTTP，直到仓库工具链满足该 SDK 文档写明的 Go 补丁版本。

后续是否增加这些能力，应根据第一阶段实际运行效果决定。

# 十七、后续开发执行计划的制定要求

本文件是总体设计规范，不直接等同于开发任务清单。

在正式制定开发执行计划前，应先完成 fast-https 现有源码分析。

## 17.1 第一步：源码能力盘点

重点检查：

- Server 生命周期和运行状态。
- Runtime 指标。
- Monitor 现有实现。
- 异常事件和告警能力。
- 日志读取接口。
- 配置管理和配置回滚能力。
- Upstream 管理能力。
- 证书管理能力。
- CLI 已有命令。
- Management API 已有接口。
- 数据持久化机制。
- 服务管理和进程部署方式。

每项能力应给出源码路径、相关类或函数、接口和实现证据。

## 17.2 第二步：形成能力差距分析

每项功能标记为：

- 已具备：可以直接复用。
- 部分具备：需要补充。
- 不具备：需要新增开发。
- 待确认：源码不足以判断。
- 不适用：当前项目不需要。

避免把已有能力重复开发。

## 17.3 第三步：确定模块边界与接口

结合源码扫描结果，明确：

- Monitor 与 Agent 的事件接口。
- Agent 与 Runtime API 的数据接口。
- Agent 与 CLI 的执行接口。
- Agent 与 Management API 的管理接口。
- Agent 内部数据持久化方式。
- DSH Plugin 与 Agent 的审批及查询接口。
- 本地模型和外部模型的调用接口。

## 17.4 第四步：拆分可执行开发任务

每项开发任务应包含：

- 任务编号。
- 所属模块。
- 任务目标。
- 现有代码基础。
- 需要修改或新增的文件。
- 接口定义。
- 数据结构。
- 前置依赖。
- 开发内容。
- 验收条件。
- 测试用例。

优先安排 P0 基础能力，待自主运维闭环通过测试后再扩展模型和更多故障场景。

# 十八、最终设计原则

fast-https AI Agent 的建设应始终遵循以下原则：

**1. 以服务器稳定性为第一优先级。**  
AI Agent 不能成为 Web Server 正常运行的依赖。

**2. 以实际运维问题为导向。**  
不以模型能力展示为目标，而以故障诊断和修复效果为目标。

**3. 确定性问题优先使用程序处理。**  
指标采集、阈值判断、权限控制和操作验证应尽可能使用原生代码。

**4. AI 负责复杂分析和计划生成。**  
利用模型处理多源信息关联、复杂故障判断和运维方案分析。

**5. 执行权必须受到独立控制。**  
模型提出建议，策略系统决定权限，受控执行器负责实际操作。

**6. 自动修复必须可验证、可追溯、可限制。**  
不能只看操作是否执行成功，还必须确认业务是否恢复。

**7. 优先复用 fast-https 已有能力。**  
先扫描现有源码，再确定需要新增什么，不重复建设。

**8. 逐步扩大自主运维范围。**  
从少量、明确、低风险的故障处理场景开始，积累真实运行数据和修复经验，再逐步扩大自动化范围。

最终目标是让 fast-https 从一个具备传统服务管理和监控能力的 Web Server，逐步发展成为具备自主诊断、受控修复和人工协作能力的智能 Web Server。
