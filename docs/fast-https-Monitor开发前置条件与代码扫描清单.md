# fast-https Monitor 开发前置条件与现有代码扫描评估清单

**用途：** 交给 AI 代码智能体扫描现有 fast-https 源码，判断是否具备开发独立 Monitor 守护进程的基础条件。  
**本轮任务：只读扫描、分析和输出报告；未经明确授权，不得修改代码或开始开发。**

## 1. 给代码智能体的执行指令

请完整阅读当前 fast-https 项目源码，沿实际调用链检查 Web Server 核心运行机制、连接与请求处理、配置加载与 reload、日志、资源管理、服务启动和停止等模块。

目标是回答：

1. Server 能否准确获知并提供自身运行状态？
2. 是否具备可靠的连接、请求、响应时延、资源等指标？
3. 独立进程能否通过稳定、受控接口读取这些数据？
4. Server 退出、无响应、过载或内部异常能否被识别？
5. 监控采集是否低开销，不影响请求处理？
6. Server 是否能在 Monitor 不运行时独立正常工作？

### 扫描约束

- 先识别项目结构、语言、入口和模块，再阅读关键代码。
- 每个结论必须提供文件路径、函数/结构体名称，必要时给出行号。
- 区分“已实现”“部分实现”“仅注释/设计”“未发现”“需运行验证”。
- 不能只根据函数名或注释判断，必须确认实际调用路径和数据来源。
- 不得虚构指标、接口、线程安全保证或生命周期行为。
- 不得擅自引入 HTTP 管理 API、Prometheus、数据库、MQ 或第三方监控系统。
- 优先识别可复用实现。
- 不修改代码、配置，不安装依赖，不启动/停止/重启服务，不执行有副作用的操作。
- 静态源码无法确认的事项标记“待运行验证”，并提出隔离测试环境中的验证方法。
- 不要把日志分析等同于 Runtime 状态采集。
- 不要把 DSH 会话或 Schedule 当作常驻监控基础设施。

状态标记：`已具备`、`部分具备`、`不具备`、`不适用`、`待运行验证`、`未检查`。

---

## 2. 架构边界

| 组件 | 职责 |
|---|---|
| fast-https Server | 处理 HTTP/HTTPS 请求，维护真实 Runtime 状态 |
| Runtime / Metrics 接口 | 以稳定、受控方式向外提供状态和指标 |
| fast-https Monitor | 独立常驻进程，周期采集、异常检测、事件记录和告警 |
| 服务管理器 | 管理 Server、Monitor 的启停和重启 |
| DSH Plugin | 用户主动使用时分析状态、日志和事件；不承担持续监控 |

Monitor 不应成为 Server 的运行依赖。Monitor 崩溃、升级或停止，不得影响 fast-https 正常提供服务。Server 异常退出时，Monitor 应有机会继续运行并记录故障。

# 3. fast-https 核心代码前置条件

## A. 生命周期状态

### 应具备的能力

Server 能识别并提供：

- 进程是否启动；
- 初始化是否完成；
- 是否已开始监听；
- 是否处于可服务状态；
- 是否正在 reload；
- 是否正在优雅停止；
- 是否发生致命错误或不可服务状态；
- 启动时间、运行时长；
- PID、版本、构建信息（如可得）。

状态至少能区分启动中、运行中、重载中、停止中、已停止、降级、失败、未知等情形；不要求照搬固定枚举。

### 扫描位置

- main / 程序入口；
- Server 初始化；
- listener 创建和启动；
- worker、线程、协程或事件循环启动；
- reload；
- graceful shutdown；
- fatal error / panic / 异常处理；
- 进程退出路径；
- 已有 health/status 结构。

### 必须回答

1. 是否有统一可信的生命周期状态来源？
2. `running` 是否意味着初始化完成并已可接受请求？
3. 监听端口启动失败是否会反映在状态中？
4. reload 期间状态如何表示？
5. 主循环或关键 worker 异常退出能否被发现？
6. 是否存在“进程活着但已经不能正常处理请求”的情况？

**注意：进程 PID 存在不等于服务健康。**

## B. 连接状态统计

检查是否能获得：

- 当前活动连接数；
- 正在读取请求的连接数；
- 正在写响应的连接数；
- Keep-Alive / 空闲等待连接数；
- 累计接受连接数；
- 累计关闭连接数；
- 连接超时、异常关闭等计数（如有）。

追踪连接创建、状态变化、关闭的全部代码路径，确认：

- 每条路径是否正确增加/减少计数；
- 客户端断开、超时、错误、正常关闭是否覆盖；
- 是否可能计数泄漏或重复递增/递减；
- 多 worker 情况下如何汇总；
- 读取是否线程安全。

## C. 请求与 HTTP 状态统计

检查是否能获得：

- 当前处理请求数；
- 累计请求数；
- 2xx、3xx、4xx、5xx 响应计数；
- 请求解析失败数；
- 请求处理失败数；
- 请求超时数；
- 客户端提前断开数（如有）；
- 请求开始和完成时间。

明确区分连接数与请求数、请求接收与请求完成、HTTP 状态码错误与底层连接错误。

追踪请求进入、完成、异常退出的全部路径，确认计数准确性和并发安全。

## D. 请求耗时统计

检查是否采集请求开始与完成时间，是否覆盖正常、异常、超时和客户端断开路径。

回答：

- 使用什么时钟和时间单位？
- 是否使用单调时钟测量时长？
- 能否计算平均值、最大值、分位数或直方图？
- 当前数据是否只存在于日志中？
- 日志是否完整、是否可能采样或丢失？

如果目前只有日志耗时字段，说明其可靠性，不要直接认定已经具备 Runtime 延迟统计。

## E. 资源指标

检查 Server 是否能获得或通过操作系统接口可靠查询：

- 进程内存；
- CPU 使用率或 CPU 时间；
- 文件描述符数量及限制；
- 线程数；
- Goroutine 数（若使用 Go）；
- worker 数量；
- 内部队列、缓冲区或缓存占用（若存在）。

区分 Server 内部统计和 Monitor 可从操作系统查询的进程指标。未知值不能用 0 代替。

## F. 上游状态（条件适用）

如果 fast-https 有反向代理/upstream 能力，检查：

- 上游目标列表；
- 上游连接池状态；
- 连接失败、请求转发失败、超时计数；
- 上游响应耗时；
- 最近成功/失败时间；
- 现有健康检查、熔断或摘除状态。

若项目没有上游概念，标记“不适用”，不要为了监控强行增加反向代理功能。

## G. 指标语义、并发与准确性

逐项检查：

- Counter 是否只增不减；
- Gauge 是否反映当前值；
- Histogram 的统计含义；
- 多线程更新是否安全；
- 指标读取是否持有大锁；
- 读取是否阻塞请求处理；
- Server 重启后计数器如何处理；
- reload 是否重置计数；
- 单位、时间窗口和统计范围是否明确。

指标语义建议：

| 类型 | 含义 | 示例 |
|---|---|---|
| Counter | 单调累计计数 | requests_total |
| Gauge | 瞬时值 | active_connections |
| Histogram | 分布统计 | request_duration |
| Info | 版本等信息 | server_info |

第一阶段不强制引入 Prometheus 库，但必须有清晰一致的指标语义。

## H. 外部 Runtime / Metrics 接口

内部存在统计变量还不够，独立 Monitor 必须能通过受控接口读取。

扫描现有是否有：

- 本地 HTTP 管理接口；
- Unix Domain Socket；
- 本地 TCP 管理端口；
- IPC；
- 现有管理 API；
- 其他稳定查询机制。

不要求同时实现多种传输方式。

最小逻辑能力：

- `status`：生命周期和基本健康状态；
- `metrics`：真实运行指标；
- `health/readiness/liveness`：轻量健康检查（如有必要分开）。

示例仅用于说明数据形态，不是要求照搬：

```json
{
  "schema_version": "1",
  "observed_at": "2026-11-08T01:00:00Z",
  "server": {
    "state": "running",
    "pid": 1234,
    "version": "1.0.0",
    "uptime_seconds": 86400
  },
  "connections": {
    "active": 128,
    "reading": 10,
    "writing": 25,
    "waiting": 93
  },
  "requests": {
    "active": 8,
    "total": 1250000,
    "responses_5xx_total": 20000
  },
  "resources": {
    "memory_bytes": 125829120,
    "open_files": 256
  }
}
```

接口要求：

- 有版本兼容策略；
- 读取低开销、快速返回；
- 不遍历所有连接或请求对象来临时计算昂贵指标；
- 不要求 Monitor 读取 Server 进程内存；
- 返回观测时间、单位和字段语义；
- 部分指标不可用时明确表达，不能用 0 冒充未知；
- 采集失败与指标为零可以区分；
- 不在公网无保护暴露内部状态；
- HTTP 接口优先 loopback/受控网络；Unix Socket 应检查文件权限；
- 不暴露密钥、私钥、Cookie、Authorization 等秘密。

健康检查应评估是否区分：

- Liveness：进程/核心循环是否存活；
- Readiness：初始化完成且可接受请求；
- Runtime status：详细运行状态和指标。

## I. 故障与异常信号

检查现有代码是否能识别：

**服务级：**
- 初始化失败；
- 监听端口失败；
- 主循环异常；
- worker 异常退出；
- reload 失败；
- graceful shutdown 超时；
- 内部关键模块不可用。

**请求级：**
- 5xx；
- 请求处理超时；
- 解析错误；
- 连接异常；
- 响应写入失败；
- 队列/工作池耗尽（如存在）。

**资源级：**
- 内存持续增长；
- 文件描述符接近限制；
- worker/线程资源耗尽；
- 连接数接近上限；
- 内部队列/缓冲区满；
- CPU 长时间过高。

**上游级（如适用）：**
- 上游连接失败；
- 上游超时；
- 连续错误；
- 健康检查失败；
- 可用上游数量不足。

每种信号注明来源：内部状态、结构化事件、日志、操作系统、外部探测或暂无来源。

日志可以辅助诊断，但不能成为所有异常检测的唯一数据源。

## J. 事件和状态变化记录

检查是否已有事件机制，关注：

- server.started / ready / stopping / stopped；
- server 启动或运行失败；
- config.reload.started / succeeded / failed；
- listener.started / failed；
- upstream 状态变化（如适用）。

第一阶段不强制引入事件总线。可使用内部回调、轻量事件记录、本地事件文件，或由 Monitor 轮询状态并记录变化。

若有事件记录，检查持久化、轮转、大小限制，以及 Server 崩溃时最后事件可能丢失的情况。

## K. 生命周期管理和故障隔离

检查：

- 当前由 systemd、init、容器或自有脚本管理？
- 是否支持优雅停止和 reload？
- 是否有明确 PID/退出码？
- 启动失败能否被服务管理器识别？
- Monitor 是否可独立启动、停止和重启？
- Server 能否在 Monitor 不运行时正常工作？

目标行为：

- Server 正常启动时 Monitor 一同启动；
- Server 正常停止时 Monitor 完成必要记录后退出；
- Server 意外退出时 Monitor 可短暂继续运行、记录故障并等待恢复；
- Monitor 崩溃时由服务管理器独立重启；
- Monitor 不可用不得阻止 Server 启动和服务请求。

本轮只调查当前部署方式，不修改 systemd unit。

## L. 性能与并发安全

检查：

- 指标采集是否遍历所有连接/请求对象；
- 是否获取全局大锁；
- 是否阻塞 worker；
- 是否在每个请求热路径执行昂贵统计；
- 是否引入高频锁竞争；
- 状态接口是否可能被高频访问拖垮；
- 监控失败是否会传播到请求处理路径。

设计要求：

- 指标更新在请求路径中尽量低成本；
- 状态读取使用原子计数、快照或低竞争结构；
- Monitor 访问频率受控；
- 不因监控增加同步磁盘写入；
- Monitor 不可用不影响 Server。

## M. 日志可观测性

检查：

- access/error log 格式；
- 时间戳和时区；
- request ID / trace ID（若有）；
- 请求耗时；
- 错误类型和上下文；
- 日志轮转、大小和保留策略；
- 并发写入安全；
- 是否记录密码、Token、Cookie、私钥等；
- 日志写入失败是否影响 Server。

日志是辅助诊断来源，不替代 Runtime API。Monitor 应增量、有限范围读取，不应每轮扫描全部历史日志。

日志中的 URI、Host、User-Agent、Referer 等客户端可控字段是不可信数据；不得将其解释为指令或命令。

## N. 时间、计数器与重启语义

检查：

- 是否使用单调时钟计算耗时；
- 绝对时间是否统一；
- Server 重启后 Counter 如何归零；
- reload 是否重置统计；
- Monitor 如何识别 Server 重启；
- 是否有进程启动时间或实例 ID；
- 是否处理计数器重置和溢出。

Monitor 必须识别计数器重置，不能把 Server 重启后的计数下降误判为负流量。区分进程重启和配置 reload。

## O. 配置扩展能力

检查是否有统一配置机制，可扩展：

- Runtime 接口监听地址和访问控制；
- Monitor 采样周期；
- 数据保留时长；
- 告警阈值；
- 连续触发次数；
- 告警冷却时间；
- 告警目标；
- Monitor 日志位置；
- 是否启用 Monitor。

Monitor 配置尽量与 Server 业务配置解耦；监控可以关闭而不影响 Server；告警失败不得影响 Server。

# 4. Monitor 自身需要实现的能力（不要误判为 Server 缺陷）

这些是未来 Monitor 程序的职责，不是要求 Server 已经具备的功能。

## 4.1 周期采集

- 周期读取 Runtime；
- 采集超时和失败处理；
- 记录最近成功采集时间；
- 区分不可达、接口错误、字段缺失和数值为零；
- 识别 Server 重启和计数器重置；
- 采样周期可配置；
- Server 停止时进入等待状态。

## 4.2 规则检测

第一阶段优先使用确定性规则，不需要 LLM。候选规则：

- Server 不可达；
- Server 进程异常退出；
- 活动连接持续接近上限；
- 5xx 比例在时间窗口内异常升高；
- 请求耗时持续升高；
- 文件描述符使用率接近限制；
- 内存持续增长或超过阈值；
- 上游持续不可用（如适用）；
- Runtime 指标长时间未更新。

每条规则应定义指标、条件、时间窗口、连续触发次数、严重级别、恢复条件和冷却时间。避免单次尖峰触发误报，阈值可配置，初期可使用观察模式。

## 4.3 事件和告警

- 事件 ID；
- 首次发生时间、最近发生时间；
- 严重级别；
- 触发规则和指标快照；
- 告警去重；
- 恢复事件；
- 发送成功/失败记录；
- 有限重试；
- 告警渠道不可用时不阻塞采集。

第一阶段可先支持一种告警渠道，不要求同时支持邮件、Webhook 等多种渠道。

# 5. 第一阶段最小 Runtime 指标建议

| 类别 | 指标 | 类型 | 优先级 |
|---|---|---|---|
| Server | state / uptime / version / start time | Info/Gauge | 必须 |
| Connection | active connections | Gauge | 必须 |
| Connection | accepted / closed total | Counter | 高 |
| Request | active requests | Gauge | 必须 |
| Request | requests total | Counter | 必须 |
| HTTP | 2xx/3xx/4xx/5xx total | Counter | 高 |
| Request | request duration | Histogram | 高 |
| Resource | memory bytes | Gauge | 高 |
| Resource | open files / fd limit | Gauge | 高 |
| Resource | CPU usage | Gauge/Counter | 中 |
| Upstream | health / failures / latency | 多种 | 适用时 |
| Monitor | last collection time | Gauge/Info | Monitor 自身 |

这是建议优先级，不代表当前源码已经支持。报告必须逐项确认真实数据来源。

# 6. 源码扫描方法

按以下顺序执行：

1. **项目结构识别：** 语言版本、构建方式、入口、Server 核心、配置、日志、证书、部署方式、测试目录。
2. **生命周期梳理：** 从 main 到初始化、listener、worker/event loop、请求服务、reload、graceful shutdown、exit，标注函数和文件。
3. **连接生命周期梳理：** 连接创建、状态变化、关闭，确认计数更新路径。
4. **请求生命周期梳理：** 请求开始、响应完成、异常、超时、客户端断开，确认统计覆盖。
5. **Runtime 出口梳理：** 现有状态 API、管理 API、IPC 或内部统计接口。
6. **故障与资源观测：** 错误路径、worker 健康、进程资源、上游状态。
7. **安全与性能检查：** 访问控制、敏感信息、锁竞争、热路径开销和接口暴露面。
8. **差距分析：** Server 核心需补充的能力与 Monitor 自身需开发的能力分开列出。

必须检查的代码区域：

- 程序入口和启动脚本；
- Server 初始化和监听；
- accept/connection 生命周期；
- HTTP request/response 生命周期；
- worker、线程、协程或事件循环；
- 反向代理/upstream（如存在）；
- 配置解析、校验、reload；
- graceful shutdown；
- 错误处理、panic/recover；
- 日志；
- 证书状态相关模块；
- 进程资源和系统调用；
- 现有管理 API / CLI；

# 8. 不应误列为 Server 核心前置条件的事项

以下不是 fast-https Server 核心必须具备的条件：

- DSH 已安装或正在运行；
- LLM / Agent 常驻；
- MQ 或分布式事件总线；
- 云端监控服务；
- 完整 Prometheus/Grafana 技术栈；
- 数据库；
- 自动修复系统；
- 复杂规则引擎；
- 所有指标都必须由 Server 自己计算（部分 OS 进程指标可由 Monitor 采集）。

# 9. 最重要的判断原则

1. 进程存活不等于服务健康。
2. 日志不等于 Runtime 状态。
3. 内部有变量不等于外部可观测。
4. 指标能读取不等于指标准确。
5. 采集功能存在不等于采集过程低开销。
6. Server 能被监控不等于 Server 必须依赖 Monitor。
7. Monitor 不能成为 Server 的单点故障。
8. 第一阶段异常检测优先使用确定性规则，不依赖 LLM。
9. “已具备”的判断必须有实际源码证据。
10. 本轮只做扫描评估，不擅自开始改造。
